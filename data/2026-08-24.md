### [1] [Portability of Fortran's 'do concurrent' on GPUs II](https://arxiv.org/abs/2608.20586)
*Ronald M. Caplan,Miko M. Stulajter,Jon A. Linker,Jeff Larkin,Nikolaos Tselepidis,Harald Servat,Shiquan Su,Giacomo Capodaglio,Johanna Potyka*

Main category: cs.PL

TL;DR: 本文探讨了使用标准Fortran语言特性（do concurrent循环）在三大GPU厂商（NVIDIA、AMD、Intel）平台上进行GPU加速的现状，通过生产级应用测试发现三家厂商均能实现纯Fortran（零指令）的GPU加速，但手动数据移动指令仍有助于提升性能和兼容性。


<details>
  <summary>Details</summary>
Motivation: HPC领域越来越倾向于使用标准语言构造进行并行和加速计算，以避免依赖供应商特定的外部API。对于Fortran应用，do concurrent循环有望让编译器实现多线程、GPU加速甚至分布式多节点代码，但其在GPU加速方面的实际成熟度需要系统评估。

Method: 使用一个生产级Fortran应用作为测试基准，在NVIDIA、AMD和Intel三大GPU供应商平台上，测试do concurrent循环的GPU加速能力。测试包括纯标准语言实现（零指令）以及结合OpenMP等指令式API的增强方案，并进行多GPU测试（使用GPU-aware MPI库）。

Result: 三大GPU厂商现在都能够对纯Fortran（零指令）代码进行GPU加速，但手动数据移动指令仍有助于提升性能和兼容性。多GPU测试使用GPU-aware MPI库完成。

Conclusion: 使用Fortran标准语言实现GPU加速的HPC科学代码正在快速进步，向着性能可移植的方向发展，但指令式API（如OpenMP）在性能和兼容性方面仍然有价值。

Abstract: There continues to be growing interest in using standard language constructs for parallel and accelerated HPC computing, avoiding the need for (sometimes vendor-specific) external APIs. For Fortran applications, language features such as 'do concurrent' loops open the door for compilers to implement multi-threaded, GPU-accelerated, and even distributed multi-node code with only the standard language. Here, we explore the current status of using 'do concurrent' for GPU-accelerated Fortran applications across three major GPU vendors (NVIDIA, AMD, and Intel). Using a production application, we test their current capabilities, showing where the standard language alone can be used, and where augmenting the code with a directive-based API (e.g., OpenMP) is still desirable or required. Multi-GPU tests are performed with GPU-aware MPI libraries. We find that the three GPU vendors can now GPU-accelerate pure Fortran (zero directives), but that manual data movement directives can help with performance and compatibility. The results show that there is rapid advancement towards making GPU-accelerated scientific HPC code performance portable using the Fortran standard language.

### [2] [Symbolic Basic Block Profiling for Machine Learning Kernels](https://arxiv.org/abs/2608.20605)
*Jingyu Qiu,Rongcui Dong,Sreepathi Pai*

Main category: cs.PL

TL;DR: 本文提出符号化程序剖析技术，为基本块执行次数生成以输入为自变量的符号公式，替代传统动态插桩剖析。该技术适用于机器学习内核程序，在LLVM编译器上实现，并在50个ML模型的78个算子（由TVM生成）上评估，其中73个内核的符号剖析结果与动态插桩完全一致，中位加速比达15093倍。


<details>
  <summary>Details</summary>
Motivation: 传统基本块剖析依赖动态插桩，存在运行时开销，且需要实际执行程序，对于大输入规模耗时严重。作者希望消除这些开销，通过符号化方法静态推导执行次数。

Method: 提出符号化程序剖析，为基本块执行次数生成以输入为变量的符号公式。该技术利用ML内核程序的结构特性，在LLVM编译器框架中实现。

Result: 在78个ML算子（来自50个ML模型，由TVM生成）上评估，73个内核的符号剖析结果与动态插桩完全一致，中位加速比达15093倍。

Conclusion: 符号化程序剖析可高效替代动态剖析，适用于ML内核类程序，在保证准确性的同时获得巨大性能提升。

Abstract: Current basic block profiling techniques obtain the count of executions of each basic block in a program using dynamic instrumentation. These profiling counters create runtime overheads and also require the execution of the program, which, for large input sizes, can take substantial time. We propose symbolic program profiling that generates symbolic formulae for a basic block's count with inputs as the independent variables. Our technique is limited in applicability to a certain class of programs, namely machine learning (ML) kernels. We implement our technique in the LLVM compiler and evaluate it on 78 ML operators from 50 different ML models. These operators are generated by TVM, a machine learning compiler. Our symbolic profiles deliver exactly the same results as dynamic instrumentation for 73 out of 78 kernels with a median speedup of 15093x.

### [3] [A Design Space Exploration of Async/Await](https://arxiv.org/abs/2608.20677)
*Gavin Gray,Shriram Krishnamurthi,Will Crichton*

Main category: cs.PL

TL;DR: 本文对"直线异步"（straight-line asynchrony）编程范式进行了设计空间探索，剖析了多个现有语言在异步函数语义上的差异，提出了涵盖异步计算全生命周期的九个设计维度，并通过具体示例、非正式设计讨论和形式语义加以阐释。


<details>
  <summary>Details</summary>
Motivation: 现代编程语言中异步编程日益普及，许多语言都提供"直线异步"（async/await）特性，表面上语法相似，但深入研究发现这些语言在多个维度上存在微妙而深刻的语义差异，导致相似的程序可能表现出不同的行为，给开发者和语言设计者带来困惑。

Method: 对多种现有语言进行剖析比较，识别出影响执行存在性和顺序的设计决策；构建由九个维度组成的设计空间，覆盖异步计算从创建到取消的完整生命周期；通过具体代码示例、非正式设计讨论以及形式语义（formal semantics）来系统化地探索和表述这些维度。

Result: 展示了没有两种语言在设计决策的全体上达成一致；提出了一个覆盖异步计算完整生命周期的九维设计空间，包括调用异步函数时的精确保证、任务生命周期结束时的行为、任务取消处理方式等问题。

Conclusion: 目标是帮助程序员、语言设计者和语言理论研究者更好地理解直线异步这一新兴领域的设计格局，为该领域未来的语言设计提供系统化的参考框架。

Abstract: Many modern programming languages include some form of asynchronous programming. In particular, a growing number now have what we call straight-line asynchrony: attempts to provide asynchronous functions that look similar to synchronous functions, thereby enabling asynchrony without introducing complex control. These languages often share construct names like "async" and "await," which suggests that they have deep semantic similarities. Yet, a close examination reveals that these languages are quite different along several dimensions, often subtly. These differences have real semantic consequences: similar-looking programs can exhibit divergent behavior, confusing developers and language designers alike.
  This paper therefore presents a design space exploration of straight-line asynchrony. We dissect several existing languages, and show how no two of them agree as a whole on design decisions that affect the presence and ordering of execution. We articulate a design space with nine dimensions covering the full lifecycle of an asynchronous computation, covering questions such as: What precise guarantees does a language give upon calling an asynchronous function? What happens at the end of a task's life? How can a task handle being cancelled? We explore these questions through concrete examples, informal design discussion, and a formal semantics. Our ultimate goal is to help programmers, language designers, and language theorists all better understand the emerging landscape of straight-line asynchrony.

</details>


### [4] [Finitary Semantics for Full Ground Local State](https://arxiv.org/abs/2608.21271)
*Orpheas van Rooij,Ohad Kammar,Sam Lindley,Cristina Matache*

Main category: cs.PL

TL;DR: 本文研究了完整地面局部状态（FGLS）的denotational模型，解决了Kammar等人的可能世界monad是否具有有限性（finitary）这一悬而未决的问题。结果表明该monad不是有限性的，但作者构造了一个有限性的子monad，并证明它为FGLS提供了充分的语义，为未来的等式公理化奠定基础。


<details>
  <summary>Details</summary>
Motivation: FGLS是许多命令式算法中的关键成分，支持存储地面值和引用的动态分配可变状态。作者希望深入理解FGLS的denotational语义，并解决一个悬而未决的理论问题：Kammar等人提出的FGLS monad是否是有限性的。这一问题对于理解monad的结构性质以及进行等式推理具有重要意义。

Method: 作者首先通过展示monad中存在非有限性的计算来证明FGLS monad不是有限性的。随后，他们构造了Kammar等人monad的一个有限性子monad，给出了该子monad的具体描述，并证明了它为FGLS提供了充分的语义。

Result: 证明了FGLS monad不是有限性的（通过构造非有限性计算的反例），并成功构造了一个有限性子monad，该子monad具备具体描述且能为FGLS提供充分的语义。

Conclusion: 通过构造一个有限性的子monad，作者为未来通过等式公理化（equational axiomatization）来理解FGLS铺平了道路，这对于程序推理具有重要价值。

Abstract: Full ground local state (FGLS) refers to dynamically allocated mutable state that allows storing ground values and references. It is a key ingredient in many imperative algorithms as it enables (cyclic) data structures. In this work, we treat full ground local state as a computational effect, focusing on one particular denotational model: Kammar et al.'s possible worlds monad on sets indexed over sets of locations. We resolve an outstanding question regarding this FGLS monad: is it finitary? We show that the FGLS monad is not finitary by showing the existence of non-finitary computations in the monad. We then introduce a finitary submonad of Kammar et al.'s monad, give it a concrete description and show that it provides an adequate semantics for FGLS. The submonad we construct paves the way to understanding FGLS in the future via an equational axiomatization suitable for program reasoning.

### [5] [An Extensive Empirical Study on Code Translation Technique](https://arxiv.org/abs/2608.20776)
*Ruihang Fan,Jiajun Jiang,Xinpeng Wang,Jiateng Fu,Fengjie Li,Jiasi Shen*

Main category: cs.SE

TL;DR: 本文通过大规模实证研究系统比较了基于学习的方法和基于大语言模型（LLM）的代码翻译技术，在方法级和类级、多语言基准上评估了可执行正确性、代码相似度、翻译方向、粒度及失败模式，发现LLM及LLM-based方法在方法级正确性上总体优于learning-based方法，但相似度指标不能可靠反映功能正确性；类级翻译显著更难，需保留全局语义、接口、成员关系和跨方法依赖；静态语义错误和逻辑错误是现有系统的主要挑战。


<details>
  <summary>Details</summary>
Motivation: 自动化代码翻译对软件演进越来越重要，但基于学习的方法与基于LLM的方法各自的优势和局限尚未被充分理解，缺乏系统性的大规模实证对比研究。

Method: 开展大规模实证研究，比较三类代码翻译技术（learning-based、LLM-based、general-purpose LLMs），在多语言的方法级和类级基准上评估，分析维度包括可执行正确性、代码相似度、翻译方向、翻译粒度和失败模式。

Result: LLM及LLM-based方法在方法级正确性上总体优于learning-based方法；相似度指标不能可靠反映功能正确性；翻译方向显著影响性能，尤其在类型系统特征不同的语言之间；类级翻译远比方法级困难；静态语义错误和逻辑错误是主要失败类型。

Conclusion: 研究结果为开发更健壮、类型感知、结构感知和上下文感知的代码翻译技术提供了实证依据和实用指导。

Abstract: Automated code translation is increasingly important for software evolution, yet the relative strengths and limitations of learning-based and large language model (LLM)-based techniques remain insufficiently understood. To address this gap, we conduct a large-scale empirical study comparing representative code translation techniques across methodological paradigms and translation granularities. We evaluate learning-based methods, LLM-based methods, and general-purpose LLMs on multilingual method-level and class-level benchmarks involving multiple programming languages. Our analysis considers executable correctness, code similarity, translation direction, translation granularity, and failure patterns. The results show that LLMs and LLM-based methods generally outperform learning-based methods in method-level correctness, although similarity metrics alone do not reliably reflect functional correctness. Translation direction substantially affects performance, particularly when translating between languages with different type-system characteristics. Class-level translation remains considerably more difficult than method-level translation because it requires preserving global semantics, interfaces, member relationships, and cross-method dependencies. Our error analysis further shows that static semantic errors and logical errors are the primary challenges in existing code translation systems. These findings provide empirical evidence and practical guidance for developing more robust, type-aware, structure-aware, and context-aware code translation techniques.

</details>

### [6] [Granthi: Higher-Order Quantum Programming via Unitary Wiring](https://arxiv.org/abs/2608.20443)
*Samson Abramsky,Radha Jagadeesan*

Main category: quant-ph

TL;DR: 本文提出 Granthi，一种纯酉高阶量子编程语言。它支持量子程序作为一等公民值进行传递、返回和相干组合；加法结构采用保留标签的路由而非观测分支，使控制可保持在叠加态；并提供有名字的可逆操作作为领域级控制空间。每个良类型项（包括函数类型）都表示其边界接口上的酉算子，编译器将其布线精确实现为物理量子比特布局上的量子电路。Granthi 已端到端实现：OCaml DSL 通过无绑定子核心 IR 经 pytket 编译为可执行量子电路，直接支持量子开关、控制流历史的干涉和结构化有限控制。


<details>
  <summary>Details</summary>
Motivation: 现有量子编程语言将高阶结构限制在经典宿主层，而量子层仅支持对量子比特的一阶操作。这种设计阻碍了量子程序自身作为可组合、可传递的一等值，也限制了控制流处于叠加态的表达能力。

Method: Granthi 基于三个设计承诺：(1) 量子程序是一等公民值，可传递、返回和相干组合；(2) 加法结构是保留标签的路由而非观测分支，允许控制保持在叠加态；(3) 提供程序员面向前端的有限标签类型与具名可逆操作，作为领域级控制空间。实现上采用 OCaml DSL，通过无绑定子核心 IR 经 pytket 后端编译为量子电路。

Result: Granthi 已端到端实现，直接支持量子开关（编译为静态电路）、控制流历史的干涉以及结构化有限控制，全部在纯酉片段内完成。每个良类型项都保证表示一个酉算子。

Conclusion: Granthi 证明了纯酉高阶量子编程语言是可行的，能够在不依赖经典观测分支的前提下实现复杂的量子控制流结构，为量子编程语言设计提供了新的范式。

Abstract: Existing quantum programming languages confine higher order structure to a classical host while restricting the quantum layer to first order operations on qubits. This paper presents Granthi, a purely unitary higher-order quantum programming language built on three design commitments: quantum programs are first class values that may be passed, returned, and coherently composed; additive structure is tag-preserving routing rather than observational branching, so control may remain in superposition; and programmer-facing finite label types with named reversible operations provide domain-level control spaces without exposing tag management.
  Every well-typed term, including at function type, denotes a unitary on its boundary interface, and the compiler realizes exactly its wiring as a quantum circuit on the physical qubit layout (assuming correctness of the pytket backend).
  Granthi is implemented end-to-end: an OCaml DSL elaborates surface programs through a binder-free core IR to executable quantum circuits via pytket. The language directly supports the quantum switch, compiled to a static circuit, as well as interference on control-flow history and structured finite control, all within the purely unitary fragment.

</details>
