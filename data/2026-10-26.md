### [1] [On the Expressiveness of Asynchronous Processes with Nested Session Types](https://arxiv.org/abs/2610.32558)
*Sjors Wortelboer,Dan Frumin,Jorge A. Pérez*

Main category: cs.PL

TL;DR: 本文证明与嵌套会话类型（NSTs）配套的异步会话进程模型 ASP 是图灵完备的，通过将二计数器机正确编码为带类型进程实现。


<details>
  <summary>Details</summary>
Motivation: 传统会话类型只能表达正则协议，无法涵盖实践中许多协议；NSTs 虽能表达嵌套递归协议（对应一计数器机与确定性上下文无关语言），但其所对应的进程模型 ASP 的表达能力尚未明确，本文旨在厘清其计算能力边界。

Method: 将二计数器机编码为带类型的异步会话进程，采用非平凡的状态感知方式表示计数器与指令，并证明该编码是正确（correct）的，从而利用 NSTs 的类型规则约束编码结构。

Result: 证明 ASP/AST 是图灵完备的：任何二计数器机计算都可由类型正确的 ASP 进程模拟。

Conclusion: 尽管 NSTs 类型层面仅刻画一计数器机与确定性上下文无关语言，但其进程模型 ASP 在类型约束下仍达到图灵完备，说明类型系统的表达能力与进程模型的计算能力之间存在显著落差。

Abstract: Session types are a type-based approach to correct message-passing programs, where types specify protocols for channels and type checking guarantees communication correctness. Traditional session types express regular protocols only, which leaves out many protocols found in practice. Aiming at overcoming this limitation, Nested Session Types (NSTs) can specify nested recursive protocols. NSTs are known to be characterised by one-counter machines and deterministic context-free languages. In this paper, we study the expressiveness of ASP (Asynchronous Session Processes), the process model associated with NSTs as introduced by Das et al. We prove that AST is Turing complete by giving a correct encoding of two-counter machines into typed processes. Our encoding uses a non-trivial state-aware representation of counters and instructions that is neatly governed by NSTs.

</details>


### [2] [On the Expressive Power of Hook-Indexed State Comprehending State in the React UI Library](https://arxiv.org/abs/2610.32925)
*Toby Ueno,Ezra Cooper,Simon Fowler,Sam Lindley*

Main category: cs.PL

TL;DR: 论文把 React 中 useState 的状态机制命名为 hook-indexed state，指出其脆弱且难以理解，提出核心演算 Lambda-React-Hook 及其类型系统以静态排除异常行为，并证明它可翻译为基于 ML 风格引用的 Lambda-React-Ref，说明钩子索引状态可由标准引用表达。


<details>
  <summary>Details</summary>
Motivation: React 是最流行的前端 JS 库，useState 通过钩子调用顺序绑定状态，实现方式既脆弱又缺乏理论解释，程序员常遇到意外行为，且这种范式的好处并不清楚。作者希望形式化其本质并提供静态保证。

Method: 定义 Lambda-React-Hook 核心演算刻画 hook-indexed state 的本质，并为其设计类型系统静态排除意外行为；随后将其翻译到基于 ML 风格引用的 Lambda-React-Ref，并证明翻译保持可类型性与语义。该翻译是局部的、可组合定义的。

Result: 证明了翻译保持类型性与语义，表明钩子索引状态可用标准引用表达；翻译虽局部且可组合，但存在显著的代码重复。

Conclusion: 该工作揭示了 React 中状态机制的本质，其观察可为未来响应式编程系统设计提供参考。

Abstract: React is currently the most popular JavaScript library for front-end web development. It endows UI components with state via the useState construct, through a mechanism that we name hook-indexed state. However, React's implementation of hook-indexed state is both fragile and poorly understood. Programmers frequently experience unexpected behavior, and the benefits of programming in this paradigm are wholly unclear.
  We define Lambda-React-Hook, a core calculus that captures the essence of hook-indexed state, and give it a type system to statically rule out unexpected behavior. We then translate Lambda-React-Hook into a calculus Lambda-React-Ref based on ML-style references, and prove that this translation preserves typability and semantics, thus showing that hook-indexed state is expressible in terms of standard references. The translation is local and admits a compositional definition, but involves significant code duplication. As well as illuminating the essence of state in React, our observations can inform the design of future reactive programming systems.

</details>

### [3] [GLP Networking API Specification](https://arxiv.org/abs/2610.32583)
*Dan Bachar,Ehud Shapiro*

Main category: cs.NI

TL;DR: 本文为 madGLP（多智能体确定性 GLP）规定其下层网络层：在 PAN/LAN/WAN 三种传输上统一接口，提供密钥派生轮换识别令牌、基于 Ed25519 的 Noise 双向认证会话、绑定握手哈希的应用度量与平台根验证，以及基于 UDP 数据报和 GATT 写入的单一消息协议，实现公平、无序、原子、可认证的交付。


<details>
  <summary>Details</summary>
Motivation: madGLP 智能体仅通过异步消息传递通信并假设公平交付，运行在个人手机上、以公钥命名，且不依赖任何全局资源（仅网络），需在 BLE、局域网与穿透 NAT 的互联网上互通；但此前未规定该网络需满足的条件及平台对网络的要求。

Method: 将网络之下可自行实现的部分尽量用 GLP 完成，网络层只提供网络栈、位置服务、应用度量和密码学原语。三种传输共用一接口：PAN/LAN 用由密钥与时间片派生的轮换识别令牌实现预接触识别与防追踪，是否回应未知联系由 GLP 设定信任级别；WAN 用可任意部署的会合服务器（无头网络层+GLP 会合智能体）协调打洞，不中继负载。各传输先由 Ed25519 密钥建立 Noise 双向认证会话，再绑定握手哈希做应用度量，直接对照 Apple/Google 根证书验证，不接触第三方。统一消息协议运行于 UDP 数据报与 GATT 写入之上。

Result: 给出了一套完整的 madGLP 网络层规范：统一接口下的三种传输下垫、隐私保护的对等发现机制、无需第三方的双向认证与应用度量链，以及满足 madGLP 公平、无序、原子、认证交付假设的消息协议。

Conclusion: 网络层被明确限定为仅补齐 GLP 无法触及的能力，其余逻辑仍以 GLP 表达；该设计在无全局资源、无需第三方信任的前提下，为 madGLP 提供了可部署、隐私友好且可验证的通信基础。

Abstract: Multiagent deterministic GLP (madGLP) runs Grassroots Logic Programs (GLP) as agents that communicate solely by asynchronous message passing, and assumes fair delivery: every message sent is eventually delivered. Each agent runs on a person's smartphone, named by the person's public key. A grassroots platform depends on no global resource but the network, so agents must reach one another over Bluetooth Low Energy, on a local network, and across the Internet from behind NAT, via rendezvous servers anyone can run. What madGLP requires of such a network, and what the network requires of the platform, has not been specified. We specify the networking layer beneath madGLP. Anything that can be done in GLP is done in GLP: the layer provides only what GLP cannot reach - the network stack, the location service, application attestation, and cryptographic primitives. Three transport underlays share one interface. Over PAN and LAN, an agent advertises a rotating recognition token derived from its key and time slot, so a peer who knows the key recognises it before contact and nobody else can track it; whether it answers unrecognised contacts is a per-underlay trust level set by GLP. Over WAN, a rendezvous server is a static-address host running the headless layer and a GLP rendezvous agent that coordinates hole punching, relays no payload, and belongs to no social graph. On every underlay, peers establish a mutually authenticated Noise session from Ed25519 keys, then attest, bound to the handshake hash, that each runs the application published under its developer's key, verified against Apple's and Google's roots with no third party contacted. One message protocol, over UDP datagrams and GATT writes, provides the fair, unordered, atomic and authenticated delivery madGLP assumes.

</details>

### [4] [Are LLM-Generated Formal Specifications Faithful to Their Requirements? A Study on Bimodal Formal Specification Generation](https://arxiv.org/abs/2610.32053)
*Wenhan Wang,Shiming Chen,Zeyu Sun,Shenghua Feng*

Main category: cs.SE

TL;DR: 本文对"自然语言需求+未知正确性代码"双模态下的LLM形式化规约生成进行实证研究，构建1403个C程序基准并用Frama-C验证ACSL规约，发现现有方法在代码错误时易生成弱规约或受实现误导而虚假通过验证。


<details>
  <summary>Details</summary>
Motivation: 现有基于LLM的规约生成工作普遍假设输入程序是正确的，这与形式化验证的真正目的（判定未知正确性的程序是否满足需求）相悖，因此需要在代码正确性未知的双模态设定下重新审视LLM规约生成的有效性。

Method: 构建包含1,403个C程序的基准，在同时给定自然语言需求与对应代码实现（正确性未知）的设定下，用Frama-C验证LLM生成的ACSL规约；并与非形式化的HoarePrompt方法对比，同时考察先进提示技术能否缓解问题。

Result: 主要发现：(1) 代码正确时，提供自然语言需求并不能提升生成规约的通过率；(2) 代码错误时，LLM会生成弱规约或受实现误导的规约从而错误通过验证，且先进提示方法无法完全缓解；(3) 相比非形式化HoarePrompt方法，LLM生成的形式化规约在预测需求-代码一致性上效果更差。

Conclusion: 本文首次将LLM形式化规约生成用于"对照需求验证程序正确性"的场景，指出"忠实于需求的规约生成"应成为未来LLM形式化规约研究的新方向。

Abstract: Formal specification generation is a critical step towards formal verification and correctness assurance of software. Recently, large language models have been widely adopted in automatic generation of formal specifications. However, existing LLM-based specification generation approaches often assume that the input program is correct, which deviates from the real purpose of formal verification---to figure out whether the program meets its requirements when its correctness is unknown. Therefore, we conduct an empirical study of LLM-based specification generation under the bimodal setting: given both the natural language requirement and its corresponding code implementation, whose correctness is unknown. We construct a benchmark of 1,403 C programs and evaluate ACSL specification generation with Frama-C verification. Our study reaches several interesting findings: first, when the code implementation is correct, providing the natural language requirement does not further improve the pass rate of generated specifications. Second, when the code implementation is incorrect, LLM-based specification generation may erroneously pass verification by producing weak or implementation-misled specifications, and this cannot be fully alleviated by advanced prompting approaches. Compared with the non-formal HoarePrompt approach, LLM-generated formal specifications are less effective in predicting requirement-code consistency. Our study takes a first look at applying LLM-based formal specification generation to verifying program correctness against requirements, and points to requirement-faithful specification generation as a new direction for future LLM-based formal specification research.

</details>
